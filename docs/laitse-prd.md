## 1. 產品定位

來坐 LaiTse 是有不同房間、能讓虛擬人物共同活動的線上共享空間。它具有辦公室或共享空間的感覺，也能用於分享、課程、社群與朋友聚會。

參與者以虛擬人物進入空間、移動並聚在同一個會議室。主講人能在房內開啟廣播、分享畫面；其他人透過按讚、「我想聽」「這個實用」、文字彈幕或圖案即時回應。

第一版必須包含簡單但真實可用的多房間、虛擬人物與進出房間能力。廣播、螢幕分享與即時互動發生在這個空間之中。

## 2. 品牌與命名

「來坐」源自日常邀請人過來坐坐的說法：可以有事討論，也可以只是一起待著。名字保留國語可理解、台語有溫度的口語感，不需要限定用途。

LaiTse 取自台語「來坐」的聲音（lâi tsē），作為品牌拼寫；不是英文直譯。品牌顯示統一為「來坐 LaiTse」，程式識別名稱建議使用 `laitse`。

- 日常邀請文案建議：**有空，來坐。**
- 品牌標語建議：**有你的位置，也有一起的空間。**
- 人物確認以像素圖呈現；尺寸、動畫方向／幀數、配色及資產來源待定。場景與一般網頁 UI 風格未一併指定。可探索椅子、圓桌或招手角色等品牌元素。
- 名稱、網域、商標及帳號可用性尚未查核。

## 3. 背景與問題

最早的需求來自科內分享：主講人投影，多數聽眾就在現場，也可能有人遠端參加。現場聽眾不必重看直播，但希望打字、按回饋或送彈幕；主講人需要看見台下的反應。

需求逐步擴大到共同虛擬空間：大家不只進入一個播放器，而是以角色聚在同一個房間，知道誰在場、活動在哪裡發生。

要解決的問題：

1. 線上活動缺乏「大家在同一個地方」的感覺。
2. 參與者需要可辨識、可切換的空間，以加入不同活動。
3. 主講人難以感受聽眾的認同、好奇與興趣。
4. 聽眾需要不打斷講者就能回應的方式。
5. 現場與遠端參與者需要共用的互動入口，但不必採用相同觀看方式。

## 4. 第一階段目標與原則

- 技術基準依 DEC-006 採 Node.js 26 LTS，涵蓋開發、建置、測試與部署；26.x 修補版及套件相容性於實作時鎖定驗證，其餘框架仍在評估。

- 自行開發來坐，不採用、fork 或客製 WorkAdventure 作產品基底；成熟框架與影音 SDK 仍可評估。
- 作為獨立服務產品，核心影音、多人狀態與身份不強制依賴供應商 SaaS；所有元件限定僅一個 Cloud Run。自研影音轉送列入可行性研究，不因此宣稱已滿足延遲、裝置、50 人或重啟保存。不得擅自另加 VM／Redis／資料庫等執行期服務；資料耐久與單一 instance 配置尚待解決。

- 建立一個可進入、有不同房間的共享場域，提供簡單的角色選擇與移動。
- 在同一個會議室內完成主講人廣播、螢幕分享及多人即時回應。
- 讓手機參與者可經房間連結直接入房，使用只互動模式。
- 讓房間管理者能控制廣播權限、公開展示與內容管理。
- 空間感與核心互動同時成立；完整地圖編輯器不是第一版前提。
- 不要求參與者先開鏡頭或麥克風；文字、圖案與回饋本身就能參與。
- 保留辦公／共享空間的感覺，應用不限企業工作。

## 5. 使用者、概念與核心流程

| 角色 | 主要能力 |
| --- | --- |
| 空間管理者 | 管理共享空間、房間與成員權限 |
| 房間主持人 | 管理房內活動、授予主講權、控制互動與展示 |
| 主講人 | 在授權房間啟動廣播與分享畫面，可與主持人為同一人 |
| 參與者 | 操控角色、加入房間、觀看／聆聽、送出文字或圖案互動 |
| 現場參與者 | 經手機直接入房，以只互動模式配合實體投影 |

**概念層級：共享空間（Space）→ 多個房間（Room）→ 房內活動（Session）。** 活動結束不代表房間或共享空間被刪除。

核心流程：

1. 管理者使用簡單預設場景建立共享空間，其中包含共享大廳與可開講的會議室。
2. 參與者開啟連結、填暱稱、選擇預設角色，進入大廳；房間深連結可直接將角色放入指定房間。
3. 參與者移動角色、選擇房間，看到房內其他角色及活動狀態。
4. 主持人開始房內活動，主講人授權麥克風後開啟廣播，並選擇分享視窗、分頁或螢幕。
5. 同房參與者選擇接收音訊與畫面，或使用只互動模式。
6. 參與者點「讚」「我想聽」「這個實用」，或明確送出彈幕／圖案；房內呈現即時效果。
7. 參與者離開房間或移到另一房，媒體與互動範圍隨之切換。
8. 主持人結束活動，停止房間廣播與分享；大家仍可留在空間交流。

## 6. MVP 功能範圍

### 6.1 共享空間、開放區域與會議室（P0）

- 第一版以預設場景起步，至少提供大廳與會議室兩個可辨識區域，且能驗證多個房間互不干擾。
- 房間顯示名稱、人數及是否正在分享，參與者能進入與離開。
- 建議一個角色同時只屬於一個房間；房間切換後更新在場狀態、訊息與媒體訂閱。
- 空間類型區分「開放空間」與「會議室」：開放空間依人物距離決定廣播接收，會議室內所有成員都可接收房內廣播。
- 會議室在場景中有可辨識的門與入口。未上鎖時無需密碼，可直接進入；上鎖時需通過密碼驗證才能進入。
- 管理者可設定會議室鎖定狀態；鎖定控制新加入，已在房內的人不因上鎖自動被踢出。密碼變更對重入授權的有效期另行設計。
- 共享空間與房間皆有可分享入口；指定房間可產生 QR Code。移動穿越門口、點選入口、直接連結與掃碼均遵守相同伺服器准入規則，不可繞過密碼。
- 房間開放／鎖定與活動狀態分開管理。空房間仍然存在。
- 不要求在第一版做任意地圖繪製、複雜家具擺設或多租戶後台。

### 6.2 虛擬人物與移動（P0）

- 暱稱加上可選的預設角色外觀，其他人可辨識是誰。
- 桌面提供簡單移動控制及明確房間入口；手機提供觸控操作或點選房間的替代入口。
- 在兩個以上真實客戶端同步位置／房間歸屬及加入、離開狀態。
- 直接掃碼入房時仍建立角色並顯示在場，不強迫現場聽眾先操控角色走完整張地圖。
- 角色支援基本回饋效果，例如舉牌、圖示或頭頂泡泡；精緻動畫可逐步提升。
- 移動不得使角色繞過准入；鎖定會議室須先通過密碼驗證。伺服器判定房間成員資格。

### 6.3 空間廣播與螢幕分享（P0）

- 主講人能直接在來坐開啟麥克風廣播與選擇螢幕分享。兩者可獨立開始／停止。
- 本版「廣播」為站內語音，依空間類型決定接收：會議室以房內成員資格為界，所有房內成員皆可收聽；開放空間以廣播者與接收者的人物距離判斷是否接收。全空間無差別公告仍列後續。
- 開放空間中，靠近至收聽範圍內才取得該廣播，離開範圍停止新增下送；採共享場景座標判斷，不能因瀏覽器縮放或鏡頭移動改變聽見範圍。距離數值與過界緩衝策略待POC設計。
- 會議室內不依人物距離裁切廣播。房外即使靠近牆或門，也不接收房內影音；房間未上鎖不代表房內聲音向外穿透。
- 範圍與准入由伺服器核對位置/空間/成員資格後決定，範圍外或未通過門禁者不應取得新影音資料，不能僅由client靜音或隱藏。
- 距離規則本次確認的是語音廣播；螢幕分享仍沿用已授權房內觀看，不新增「靠近自動彈出畫面」需求。
- 建議每房同時一位主講人發送廣播及一個畫面來源，主持人可授權切換；多主講與多人通話不在第一版要求內。
- 房內顯示誰在廣播、誰在分享，以及媒體接收狀態。瀏覽器要求使用者操作才能播放時提供明確的開始聆聽入口。
- 分享被瀏覽器停止、權限遭拒、主講人斷線時，所有接收端顯示正確狀態，文字互動繼續可用。
- 離開房間時取消該房媒體訂閱；正在廣播或分享者離房時，建議先確認並停止發布，不將來源自動帶到新房。
- 已在房內者被移除或權限撤銷後，必須撤銷媒體發布／接收權限，不能只隱藏播放器。
- 可選擇開源自架即時影音引擎或其他可獨立部署的傳輸方案；不要求自行開發影音底層，不以第三方影音 SaaS 作為核心必要依賴。
- 外部直播嵌入可作補充，但不能代替「站內開啟廣播與分享畫面」的驗收。
- 攝影機視訊、錄影、隨選影片及完整多人會議通話列後續。開放空間的距離廣播已依DEC-011納入核心，並非完整多人雙向通話已定案。

### 6.4 觀看與只互動模式（P0）

- **觀看＋互動**：顯示分享畫面、廣播接收與互動控制，仍能知道房內成員。
- **只互動**：以按鈕、文字與圖案輸入為主，不訂閱廣播／分享媒體，適用實體會議室。
- 只互動模式預設不播放聲音，避免多人裝置造成回音；可主動切換模式。
- 模式切換不改變角色房間歸屬、不清空草稿，也不要求重新加入。
- 進入觀看模式時尊重播放權限與使用者音量選擇，不突然有聲播放。

### 6.5 回饋、圖案與彈幕（P0）

- 預設回饋：👍 **讚**、👂 **我想聽**、💡 **這個實用**。使用者原文「我向聽」依語意整理為「我想聽」。
- 點擊立即顯示本機操作狀態，伺服器接受後同步同房參與者及展示端。
- 效果可呈現在角色頭頂及房內觀看畫面的互動層，避免重要內容被遮住。
- 支援純文字聊天、明確選擇公開的文字彈幕，以及固定圖案／表情。第一版不要求使用者上傳自訂圖片。
- 聊天列表與彈幕目的地要清楚，聊天不自動變成投影彈幕。
- 主持人可開關彈幕、暫停展示、清空待播佇列與移除內容；暫停與禁止新增為不同操作。
- 高密度事件聚合顯示；彈幕佇列有上限及過期時間，重連時不補播過期效果。
- 建議聊天 300 字、彈幕 60 字、每人每秒接受一次回饋，為可調整的初始值；限制須在伺服器執行。
- 重送相同事件不重複計數；統計分清互動次數與不重複參與者。

### 6.6 主持、權限與展示（P0）

- 管理身份與參與身份分開授權，知道房間網址不等於擁有主持權。
- 主持人可授予／撤回主講權、停止房內分享、限制互動、移除參與者及鎖定加入。
- 移除訊息後，同步移除訊息列表與待播彈幕；已被看過的內容無法收回。
- 展示端提供獨立全螢幕視圖，顯示分享內容、房內反應及加入 QR Code，不暴露管理功能。
- 展示端與角色共享同一房間狀態；展示端不是主講身份，不需開麥。
- 跨應用程式覆蓋 PowerPoint／Keynote 不屬於瀏覽器展示頁自帶能力；先以分享簡報視窗並在來坐展示頁呈現為建議方案。

### 6.7 連線、可及性與裝置（P0）

- 依 DEC-005，可用 Cloud Run 最小執行個體維持暖機，接受連線中斷後自動重連；恢復時重新驗證身份／房間／權限、同步狀態並重建必要媒體。暖機不保證程序永不重啟；此確認不代表接受持久資料遺失。

- 桌面與手機完成核心加入、選房與互動，不依賴滑鼠懸停。
- 支援鍵盤、可讀文字對比及減少動態效果偏好。
- 斷線時顯示狀態，不能假裝事件成功；重連後同步權威房間歸屬、近期訊息與統計。
- 重連不得復活已撤銷的主講權或重新發布媒體；依最新權限重新建立接收。
- 瀏覽器／裝置不支援發布螢幕時明確告知，仍可使用接收與互動。發布能力的支援矩陣於技術驗證後記錄。

## 7. 狀態與概念資料模型

| 概念 | 用途 |
| --- | --- |
| Space | 一個共享場域，包含多個房間與管理權限 |
| OpenArea | 開放空間；廣播接收依人物距離，範圍參數待定 |
| Room / MeetingRoom | 會議室；成員、媒體、訊息與互動的邊界，房內廣播全房接收 |
| Door | 會議室入口；未鎖直接進入，上鎖需密碼驗證；准入由伺服器判定 |
| Participant / Avatar | 參與身份、暱稱、外觀、目前房間、位置及連線狀態 |
| Session | 房內一次活動，狀態為準備中、進行中、已結束 |
| Broadcast / ScreenShare | 發布者、房間、活動、授權與啟用狀態；憑證不下發給未授權者 |
| Message / ReactionEvent | 送出者、房間、活動識別、事件去重碼、目的地及管理狀態 |

建議：一般房間聊天在活動前後皆可使用；活動期間的彈幕與回饋綁定該次 Session。活動結束停止該次廣播、分享與活動回饋，房間和日常聊天仍存在。此細節為設計提案。

## 8. 後續範圍

- 可互動物件、白板、資源看板與小遊戲。
- 完整多人雙向語音／視訊、全空間公告與無差別廣播；開放空間的距離廣播已納入核心。

## 9. 驗收情境

1. 至少兩個真實客戶端能在同一共享空間看到彼此角色、移動與進出房間。
2. 能在兩個房間分別開活動；A 房的音訊、分享、文字、彈幕及圖案不傳到 B 房。
3. 掃描會議室 QR Code 可直接入房，角色出現在正確房間，手機能只互動而不接收影音。
4. 主講人能在站內授權麥克風與螢幕，房內遠端參與者能聽見並觀看；外部播放器不能替代此測試。
5. 廣播與分享可獨立停止；拒絕權限、分享中止及來源斷線皆有清楚狀態，聊天不被中斷。
6. 參與者按「讚」「我想聽」「這個實用」或送文字／圖案後，同房展示端同步效果。
7. 切房會停止接收舊房媒體並切換互動範圍；離房中的主講人不會繼續向舊房或新房意外發布。
8. 未授權者不能啟動廣播、改房間設定或接收鎖定房間內容；伺服器及影音授權共同驗證。
9. 主持人撤回主講權、移除參與者或關閉彈幕後，各端遵守狀態，重新整理不會繞過限制。
10. 重送事件不重複計數；重連不補播過期彈幕、不恢復過期發布權限。
11. 結束 Session 後媒體停止，但房間仍存在，角色可留在裡面或離開。
12. 手機可選房與互動，減少動態模式可停用非必要動畫。
13. 開放空間中兩個真實客戶端靠近時可接收廣播，離開範圍後停止新增下送；偽造位置或僅修改client收聽條件不能取得範圍外廣播。
14. 會議室未鎖可直接進入；上鎖後無密碼/錯誤密碼不能進入或接收房內內容，正確密碼才可進入。移動/深連結/QR入口遵守同一規則。
15. 進入會議室後，即使角色相距較遠，房內成員仍可接收廣播；門外角色即使靠近也收不到。

建議首輪以每共享空間 50 人同時在線測試，涵蓋集中在一房及分散多房；互動事件從伺服器接受至接收端顯示的 p95 目標為 1 秒內。此數字尚未經容量驗證，影音延遲、畫質及房間上限須另做技術測試，不能宣稱已達標。

## 10. 成效與資料

- 觀察加入完成率、入房耗時、廣播／分享成功率、觀看中斷率、互動參與比例與跨房交流情況。
- 訪談主講人與聽眾是否感到共同在場，以及彈幕是否干擾分享。
- 分析優先採聚合事件；不為統計而額外保存聊天全文或錄製影音。
- 暱稱、角色狀態、訊息與活動資料的保存期限、刪除方式及告知文案須在真實試用前確定。
- 暱稱重新加入造成的濫用風險須記錄，依測試結果決定邀請驗證與成員身份機制。

## 11. 建議交付順序與待決事項

依 DEC-007／DEC-008，**先做分階段 POC，再進入 MVP 開發**。POC 僅本機開發與測試、不部署 Cloud Run；主要邊界為真實瀏覽器經本機單一應用到另一真實瀏覽器。POC 執行時同步紀錄每次實驗、失敗與可復用方案，依 [POC 計畫書](poc/plan.md) 進行；以下是通過 POC 後的 MVP 功能交付順序，不表示目前已啟動。後續產品仍以單一 Cloud Run 為部署目標，本機通過不等同雲端通過。

1. **共享空間切片**：預設場景、角色、移動、兩個房間、直接入房與真實多人同步。
2. **同房開講切片**：授權主講、站內廣播／分享畫面、房間隔離與觀看／只互動切換。
3. **互動與主持切片**：三種預設反應、文字／圖案彈幕、展示端及管理能力。
4. **真實分享試用**：測手機、影音權限、投影流程、網路及跨房操作；必要時迭代空間操作。

這是實作順序，以上切片共同構成 MVP；第一個切片不是完整可交付產品，也不是工期承諾。

優先待決：

- 開放空間廣播距離、邊界行為與多來源接收；密碼更新/重入授權與門口互動細節。

- 人物像素圖已確認；人物資產規格、場景視覺、移動控制及房間轉場方式待定。
- 影音傳輸服務、成本、部署環境及裝置支援；站內廣播／分享的需求已明確，不再以外部嵌入當作預設答案。
- 主辦者登入、訪客身份與邀請連結的存取控制。
- 房間上限、預期規模、資料保存與刪除政策。
- 展示端如何搭配現場簡報；是否另需外部軟體疊加。
