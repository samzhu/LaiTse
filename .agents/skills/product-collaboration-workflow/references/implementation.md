# 實作與驗證

編輯前先檢視目前行為與相關需求，並將變更限制在記錄的範圍內。授權範圍內例行且可回復的技術選擇由負責人決定；產品行為、範圍擴張、重大風險或共用資源衝突則回報處理。

## 小步驗證與累積

每步先對應既有產品目標，選一個能操作、能觀察結果的最小閉環，寫清本次要釐清的問題與完成條件。優先沿用可執行基底，把可延續部分接回既有流程，並核對與前一步的資料、介面及狀態相容。需要拋棄式實驗時，保留結論與採用理由，避免預先建立尚無實際用途的抽象。

探索型 POC 先回答「核心做得到嗎、怎麼使用、還有哪些限制」。驗測做到足以判斷下一步即可；依當次要求與實際風險補充品質、效能或長時間檢查。涉及正式修正或商品交付時，採用相符的驗收強度，必要的產品條件仍依權威需求判斷。

實作時同步沿用既有紀錄，留下實際入口／操作步驟、版本與條件、代表證據、失敗與修正，以及商品採用前尚需補齊的工作。缺少裝置、權限或可靠量測時，交付可驗部分並明列未驗範圍；模擬、合成或單點結果只支持其實際驗證的結論。

讓程式、操作說明與驗測紀錄維持同一可追溯版本。依使用者或專案既有提交約定，將該步的程式及必要紀錄一起 commit；推送、合併與發布另依授權處理。

## 整合成完整商品

在已授權的整合階段，依累積證據判斷哪些介面、模組與測試可保留、需重構或應移除；整理固定測試資料、偵錯控制與模擬入口。沿用既有權威需求及交接紀錄，讓實驗中學到的方法成為可維護的產品實作。

以最終使用者的完整流程驗證跨功能整合，核對資料、狀態、權限與錯誤恢復是否一致，再依商品目標補足必要裝置、保存與品質驗收。各步可行不直接等於整體商品可交付；只有出現新差異、失敗或風險時才擴大或重跑已完成的驗測。

## 選擇檢查與保存證據

選擇能驗證變更行為且符合風險的檢查。網頁例子：受影響模組跑 lint／型別檢查，局部邏輯跑單元測試，系統邊界跑整合測試，使用者流程（如表單驗證或登入）則在可行時實際操作瀏覽器。文字調整不必跑所有檢查，並說明哪些未執行。測試通過不等於人類接受或已部署。

工具寫入或持久化操作後，讀回保存結果。操作錯誤或中止時先檢查狀態，再做一次最小受控診斷。相同錯誤再現或證據矛盾時，停止該操作；不要無限重試或繞過存取限制。安全時可繼續無相依工作。

絕不可把 mock 值或未實作 API／事件／資料標成即時資料。在開發文件或設計註記記錄來源與限制，不要在使用者介面加入干擾資訊。

## 工作階段接續

若需壓縮上下文、重設或交接，先更新精簡 checkpoint，保留目標、授權範圍、已確認事項、未完成工作、重要界線、權威路徑及資源交接狀態。之後只使用環境實際提供的官方接續能力；不要聲稱摘要等同完整對話，也不要因上下文重設而刪除對話或紀錄，除非明確獲得授權。

確認事件的背景回寫只有在實際執行者開始處理時，才能標為進行中。尚未啟動時標為已收到／排隊；中止時記錄中止與保存狀態。寫入後讀回核對，再標為已保存。這項工作不阻擋人類明確要求且資源獨立的下一項；不得以等待確認回寫為由阻擋或自行切換項目。

完成時回報：

1. 修改內容與本步釐清的問題。
2. 操作／重現方式、證據位置及保存／讀回狀態。
3. 通過與未執行的檢查。
4. 已同步的文件與可延續的方案。
5. 商品採用前的限制、待決事項或阻擋，以及下一步建議。
6. 每項資源已釋出或已交接。
